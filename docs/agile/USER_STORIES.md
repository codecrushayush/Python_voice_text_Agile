# User Stories

**Project:** Python Text-to-Speech, Speech-to-Text and Virtual Assistant
**Document Owner:** Product Owner (student developer)
**Version:** 1.0 — Final (all four sprints completed)

This document records the 15 user stories that describe the user-visible behaviour of the
system. Each story is written in the standard "As a / I want to / So that" form, carries a
priority (High, Medium or Low), an effort estimate on the Fibonacci-like scale
{1, 2, 3, 5, 8}, and the sprint in which it reached the Definition of Done. Acceptance
criteria are expressed as verifiable check boxes so that they can be walked through during
the Sprint Review.

---

## US-01
**As a** user,
**I want to** enter text and convert it into speech,
**so that** I can listen to the written text.

- **Priority:** High
- **Story Points:** 8
- **Sprint:** Sprint 1
- **Acceptance Criteria:**
  - [ ] User can type text into the text area of the TextToSpeech page
  - [ ] Empty or whitespace-only text cannot be submitted (validated in `TextToSpeech.jsx` and again in `backend/app/schemas/tts.py`)
  - [ ] Input longer than 5000 characters is rejected with a friendly message
  - [ ] Speech is generated by `POST /api/tts` through `backend/app/services/tts_service.py`
  - [ ] Audio can be played in the `AudioPlayer` component as soon as generation finishes
  - [ ] Audio can be downloaded as a file
  - [ ] The conversion is written to the `conversion_history` table with `type = 'tts'`

## US-02
**As a** user,
**I want to** choose the language and the speech rate of the generated voice,
**so that** the audio matches my preferred language and reading speed.

- **Priority:** Medium
- **Story Points:** 5
- **Sprint:** Sprint 1
- **Acceptance Criteria:**
  - [ ] Language select box is populated from `GET /api/tts/languages`
  - [ ] Engine select box lets the user choose gTTS (online) or pyttsx3 (offline)
  - [ ] Rate slider covers 80–300 words per minute and displays the current value
  - [ ] Changing language, engine or rate regenerates the speech with the new values
  - [ ] Default language and default rate from the Settings page pre-fill the controls

## US-03
**As a** user,
**I want to** play, replay and download the generated audio,
**so that** I can review and keep the speech output.

- **Priority:** Medium
- **Story Points:** 5
- **Sprint:** Sprint 1
- **Acceptance Criteria:**
  - [ ] Audio can be played and paused from the `AudioPlayer` component
  - [ ] A replay control restarts the audio from the beginning
  - [ ] A download button saves the file with a meaningful file name
  - [ ] The player shows no crash state when no audio has been generated yet
  - [ ] Playback works in the supported desktop browsers (Chrome, Edge, Firefox)

## US-04
**As a** user,
**I want to** record my speech with the browser microphone and have it converted to text,
**so that** I do not have to type long passages.

- **Priority:** High
- **Story Points:** 8
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] `MicrophoneButton` requests browser microphone permission
  - [ ] Recording captures audio through `frontend/src/utils/recorder.js`
  - [ ] An elapsed-time indicator and a recording indicator are visible while recording
  - [ ] The recording is uploaded as multipart/form-data to `POST /api/stt`
  - [ ] Recognised text is returned and displayed on the SpeechToText page
  - [ ] Permission denial produces a friendly toast message instead of a crash

## US-05
**As a** user,
**I want to** upload an existing audio file to be converted into text,
**so that** I can transcribe recordings I already have.

- **Priority:** High
- **Story Points:** 5
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] User can select an audio file from the file system
  - [ ] Only WAV, MP3, OGG, WebM, FLAC and M4A files are accepted
  - [ ] Files larger than 10 MB are rejected with a friendly message
  - [ ] Unsupported formats are rejected before any processing takes place
  - [ ] Recognised text is displayed and stored in `conversion_history` with `type = 'stt'`

## US-06
**As a** user,
**I want to** view the recognised text and copy or download it,
**so that** I can reuse the transcription elsewhere.

- **Priority:** Medium
- **Story Points:** 3
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] Recognised text appears in the result area of the SpeechToText page
  - [ ] A copy button places the text on the clipboard and shows a confirmation toast
  - [ ] A download button saves the text as a `.txt` file
  - [ ] A reset control clears the text, the audio and the recording state
  - [ ] An empty state is shown before any speech has been transcribed

## US-07
**As a** user,
**I want to** type commands into the virtual assistant,
**so that** I can obtain quick answers and actions.

- **Priority:** High
- **Story Points:** 5
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] User can type a command and submit it from `frontend/src/pages/Assistant.jsx`
  - [ ] `POST /api/assistant` matches all ten rules: hello/hi, what time is it, what is today's date, open Google, open YouTube, search Google for ..., help, about application, clear
  - [ ] Responses are produced by the rule engine in `assistant_service.py` with no AI/ML/LLM involved
  - [ ] Each message displays a timestamp
  - [ ] Command chips insert a ready-made command into the input
  - [ ] The `clear` command empties the conversation
  - [ ] Unrecognised input returns the friendly fallback response

## US-08
**As a** user,
**I want to** speak my command to the virtual assistant,
**so that** I can interact with it hands-free.

- **Priority:** Medium
- **Story Points:** 3
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] A microphone control is available inside the Assistant page
  - [ ] Speech is transcribed into the command input before submission
  - [ ] The transcribed command passes through the same rule engine as typed input
  - [ ] Failure of speech capture falls back to typed input without losing the conversation

## US-09
**As a** user,
**I want to** hear the assistant speak its response,
**so that** the interaction feels like a conversation.

- **Priority:** Low
- **Story Points:** 2
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] The assistant response is read aloud after each successful command
  - [ ] Speech output respects the auto-play toggle stored in Settings
  - [ ] Absence of a speech synthesis engine degrades gracefully to text-only output

## US-10
**As a** user,
**I want to** view the history of all my conversions,
**so that** I can revisit previous text-to-speech, speech-to-text and assistant activity.

- **Priority:** High
- **Story Points:** 5
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] The History page lists records retrieved from `GET /api/history`
  - [ ] Each row shows type, input text, output text and creation timestamp
  - [ ] Records are paged through the `limit` and `offset` query parameters
  - [ ] An empty state is shown when no record exists
  - [ ] Newly completed conversions appear without manual refresh

## US-11
**As a** user,
**I want to** search and filter my history,
**so that** I can find a specific conversion quickly.

- **Priority:** Medium
- **Story Points:** 2
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] A search box filters records by input and output text
  - [ ] A type filter restricts results to TTS, STT or assistant records
  - [ ] Filtering and searching combine and are executed server side (`type`, `search` parameters)
  - [ ] The number of matching records is displayed

## US-12
**As a** user,
**I want to** delete a single history record or clear the whole history,
**so that** I can remove data I no longer need.

- **Priority:** Medium
- **Story Points:** 2
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] Deleting a row opens the `ConfirmationModal` dialog
  - [ ] Confirming calls `DELETE /api/history/{id}` and removes the row
  - [ ] Cancelling closes the dialog without deleting anything
  - [ ] Clear all calls `DELETE /api/history` with the selected `type` parameter
  - [ ] Both actions raise a toast notification confirming the result

## US-13
**As a** user,
**I want to** see statistics and my recent activity on the dashboard,
**so that** I get an overview of my usage at a glance.

- **Priority:** High
- **Story Points:** 3
- **Sprint:** Sprint 2
- **Acceptance Criteria:**
  - [ ] Stat cards are populated from `GET /api/stats` (total, TTS, STT and assistant counts)
  - [ ] Quick action links navigate to the TextToSpeech, SpeechToText and Assistant pages
  - [ ] The recent activity list shows the latest conversions from `conversion_history`
  - [ ] A loading spinner is displayed while statistics are being fetched

## US-14
**As a** user,
**I want to** switch between light and dark mode and set my speech preferences,
**so that** the application matches my working environment.

- **Priority:** Medium
- **Story Points:** 5
- **Sprint:** Sprint 3
- **Acceptance Criteria:**
  - [ ] The theme toggle switches the whole application between light and dark mode
  - [ ] Default language, default speech rate and the auto-play toggle can be changed on the Settings page
  - [ ] Preferences persist across reloads through `frontend/src/context/SettingsContext.jsx` and `localStorage`
  - [ ] The backend status indicator reports the result of `GET /health`
  - [ ] Preferences are applied to new TTS requests and assistant speech output

## US-15
**As a** user,
**I want to** receive friendly error messages on any screen size,
**so that** I can recover from problems without technical knowledge.

- **Priority:** High
- **Story Points:** 3
- **Sprint:** Sprint 3
- **Acceptance Criteria:**
  - [ ] Backend exceptions raised in `backend/app/utils/exceptions.py` are returned as readable messages
  - [ ] Errors are surfaced as toast notifications through the `Toast` component
  - [ ] The sidebar collapses to an icon rail on tablet and mobile viewports
  - [ ] No horizontal scrolling occurs at a viewport width of 375 px
  - [ ] Empty states guide the user on the Dashboard, History and Assistant pages

### Reconciliation Note

Story-level sprint allocation (Sprint 0: 0, Sprint 1: 18, Sprint 2: 38, Sprint 3: 8) differs
from the task-level sprint totals used in `PRODUCT_BACKLOG.md` and `SPRINT_PLAN.md`
(8 / 18 / 22 / 16). The difference is intentional: Sprint 0 contains only technical
enablers that map to no single user story, and the testing, refactoring, CI and
documentation work executed in Sprint 3 supports stories that were already functionally
complete. Both decompositions total exactly 64 points.
